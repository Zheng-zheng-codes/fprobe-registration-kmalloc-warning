# WARNING in register_fprobe_ips (mm/slub.c:5459, v7.4-rc2)

Syzkaller-found bug on Linux v7.4-rc2, reproduced and verified on the same
kernel build. Externally reproduced **3/3 times** on fresh VMs (see
"Verified runs" below).

## Summary

A warning fires during fprobe registration while the kernel is performing
a large kmalloc:

```
WARNING: mm/slub.c:5459 at ___kmalloc_large_node+0x13f/0x180 mm/slub.c:5459, CPU#2: syz.4.4204/72997
RIP: 0010:___kmalloc_large_node+0x13f/0x180 mm/slub.c:5459
```

The warning is triggered inside `___kmalloc_large_node()` (mm/slub.c:5459)
by a ~32 MiB kzalloc request from `register_fprobe_ips()` during BPF
kprobe-multi link attachment. The guest runs with `panic_on_warn=1`, which escalates this
warning to a kernel panic.

## Key technical evidence

Program 78 in the reproducer set contains the triggering BPF operation:

```
r0 = bpf$PROG_LOAD(0x5, ...)   // BPF_PROG_TYPE_KPROBE
bpf$BPF_LINK_CREATE_XDP(0x1c, ..., @kprobe_multi=@addrs={...}, ...)
```

The `@kprobe_multi` branch specifies `cnt = 0x100000` (1,048,576), which
exactly matches `MAX_KPROBE_MULTI_CNT` (`1U << 20`, defined in
kernel/trace/bpf_trace.c:45). The request passes the existing count limit
check (`cnt > MAX_KPROBE_MULTI_CNT` at bpf_trace.c:2846) and proceeds to
`register_fprobe_ips()`, which calls `kzalloc_flex(*hlist_array, array,
num)` (kernel/trace/fprobe.c:918) with `num = 0x100000`.

The crash registers show the allocation size:

```
RDI: 0x2000030  (= 33,554,480 bytes ≈ 32 MiB + 48 bytes header)
R13: 0x100000   (= cnt)
```

This matches the fprobe allocation:
`sizeof(struct fprobe_hlist) + num * sizeof(struct fprobe_hlist_node)`
= 48 + 0x100000 × 32 = 0x2000030 bytes ≈ 32 MiB. The allocation passed the BPF count limit but the resulting
~32 MiB kzalloc triggered the SLUB size check WARNING.

## How to reproduce

### Prerequisites

1. Boot a Debian trixie x86_64 VM (6 GiB RAM, 4 vCPU, KVM) using the QEMU
   command line in `environment.txt`, with the kernel built from v7.4-rc2
   (see `kernel.config`; CONFIG_KASAN=y).
2. Copy `syz-execprog` and `syz-executor` (built from syzkaller commit
   `853b104bb454141a5b0fc0e4218ec78e9f34ffb1`) into the guest.
3. Copy `reproducer/repro.kernsight.prog` into the guest.

### Run

In the guest, as root:

```sh
syz-execprog -procs=8 -threaded -repeat=1 -executor ./syz-executor repro.kernsight.prog
```

### What you will see

After **~2-13 minutes** the serial console (or `dmesg`) will show:

```
WARNING: mm/slub.c:5459 at ___kmalloc_large_node+0x13f/0x180 mm/slub.c:5459, CPU#N: syz.N.NNN/NNNNN
```

followed by a kernel panic (escalated by `panic_on_warn=1`).

## Why the reproducer is a multi-program set

The WARNING depends on kernel state built up by preceding operations
(including `syz_mount_image$jfs` and fprobe registration). The 84-program
set constructs the required state before the triggering operation.
